# 0021 — AI Management Reports as Module 07

- Status: Accepted
- Date: 2026-10-24

## Context

ADR-0020 pulled the dashboard forward, shipped D1 with deterministic fixtures and D2 with real read
endpoints. Its D3 was described as “wire the `ai/` service” — a single dashboard block with a
three-second rules fallback. That framing no longer matches the product need:

- The client wants **management reports as a home**, not one card inside the dashboard.
- The report needs **variants** (executive, pipeline, client health), which is a page-level concern.
- AI will grow into later submodules (record summaries, message drafting), so the surface needs an
  owner and a navigation section.
- The system has **no AI budget**. Any external generation must work inside a free tier, and the
  product must remain complete when the provider is unavailable.
- CRM data is sensitive. A free tier is not a licence to send contact names, notes or message bodies
  to a third party.

The existing `ai/` service is a FastAPI scaffold with only `/health`; the dashboard's “AI” report is
Laravel rules. There is no model integration to preserve.

## Decision

1. **AI Management Reports is Module 07, with its own spec and page.** It is a read-only presentation
   module over modules 01–06, owns no table, and lives in `specs/15`. It gets a **AI Reports** sidebar
   group and `/reports`; future AI submodules join the same group. It is not a data module and does
   not change any module's rules.

2. **Three variants, one page.** Executive, Pipeline and Client Health are tabs on `/reports`, all
   scoped like the dashboard. Team Performance is deferred because it mixes CRM output with core2 HR
   data and needs its own sensitivity rules.

3. **Rules first, model second.** The standard report is generated by Laravel for all three variants
   and is always available. The model is an optional prose layer behind the same response shape. S1
   ships the module and rules variants alone; S2 adds generation. If S2 is disabled, the product is
   still complete.

4. **Groq free tier is the only provider in S2.** Groq is OpenAI-compatible, needs no credit card and
   currently offers roughly 30 RPM / 1,000 requests per day / 8K TPM / 200K TPD. Its current terms
   are more privacy-friendly than Gemini's free tier; verify retention/training terms and enable
   zero-retention where available. The model is configurable
   (`openai/gpt-oss-20b` by default). Gemini free-tier data may be used to improve Google products,
   so it is not the default for CRM data. OpenRouter free models are too limited (50/day without
   credits) to be a primary. A local Ollama model remains an option if the client later requires
   offline operation; it is not the demo default.

5. **Fallback is Groq → rules, not Groq → another free provider.** A second provider doubles the
   privacy and quota surface for little benefit. Timeout, 429, missing key, provider error and invalid
   JSON all return the rules report. A second provider can be added behind the same seam later if the
   client accepts it.

6. **Generation is on demand and cached.** Page load uses `GET /reports/management`, which never calls
   the provider and returns the cached model report when one exists, otherwise the rules report.
   `POST /reports/management/generate` is the only path that spends tokens. Reports are cached by
   user + range + variant + context hash for 15 minutes; refresh has a 5-minute cooldown. Per-user
   (30/day) and org (800/day) caps sit below the free-tier ceiling. There is no retry on 429 or
   timeout.

7. **Only aggregated, PII-free context leaves Laravel.** The provider receives counts, periods, scope
   labels, stage labels, win/loss and worklist counts — never account names, contact names, emails,
   notes, message subjects/bodies, staff names or record IDs. The model returns prose and allowed
   insight/action IDs; Laravel maps IDs to real routes. The frontend never supplies context.

8. **The fallback is visible, the provider error is not.** When `source = rules` and a fallback reason
   exists, `/reports` shows an inline info alert: “AI report is unavailable right now — showing the
   standard management report.” This is a degraded-state message, not a simulation label. Raw
   provider errors stay in the server log. `AI_REPORT_ENABLED=false` demonstrates the path without
   deleting a key.

9. **The dashboard card stays the standard summary.** It gains a link to `/reports` and does not call
   the provider. This keeps the dashboard fast and avoids paying twice for the same narrative.

10. **The service stays lightweight.** FastAPI + `httpx` + Pydantic; no LangChain, LlamaIndex,
    embeddings, vector database, PyTorch, fine-tuning or RAG. Structured JSON is produced with the
    provider's JSON mode and validated by a Pydantic schema. Token counts and latency are logged; the
    prompt itself is not persisted.

## Alternatives rejected

- **Keep D3 as one dashboard card.** Cheap, but no home for variants and future AI submodules, and it
  forces generation into the dashboard request path.
- **Generate on every dashboard load.** Highest risk of burning the free quota, and a slow provider
  would degrade the main screen.
- **Gemini free tier as the default.** Strong model, but free-tier inputs may be used to improve
  Google products; not appropriate for CRM data without explicit client approval.
- **OpenRouter free models as the primary.** The free allowance is too small and provider routing
  makes privacy harder to explain.
- **Groq → OpenRouter/Gemini fallback.** Adds another vendor and another data path for a failure mode
  that the rules report already handles.
- **Local Ollama as the demo default.** No external data path, but adds a multi-GB model and hardware
  requirement to a system that should stay lightweight. It remains a configurable future provider.
- **LangChain / LlamaIndex / RAG.** The context is structured numbers, not documents. They add
  dependencies, prompt indirection and failure modes without improving the report.
- **Persist reports in a table.** The report is derived; caching is enough. A table would create stale
  copies, another permission surface and another migration.
- **Let the model write URLs.** It would eventually invent a dead link. Fixed IDs mapped by Laravel
  keep every action real.
- **Auto-send or auto-apply the suggested actions.** Reports are advisory. The module links to the
  page that owns the action; it never mutates a record.

## Consequences

- `specs/15-ai-management-reports.md` owns S1/S2 and the future S3/S4 slots.
- Spec `14` keeps D1 + D2; its D3 is a pointer to Module 07. The dashboard `ai` block remains the
  rules summary and gains a link to `/reports`.
- New frontend route `/reports` and a sidebar **AI Reports** group. No new backend table, no
  migration and no change to modules 01–05.
- `ai/` gains `POST /reports/dashboard`, a provider adapter and tests. `GROQ_API_KEY` lives only in
  the service environment.
- The demo can show both paths: a real Groq report with a key, and the standard report plus info alert
  with the key removed or `AI_REPORT_ENABLED=false`.
- Free-tier limits and model names can change. They are configuration, not contract; the provider seam
  and the rules fallback are the stable parts.
- The PII-free context is a deliberate limitation: future variants that need names must extend the
  contract explicitly, not silently widen the prompt.
